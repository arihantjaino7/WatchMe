This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WatchMe AI — "Strava for knowledge work." A Chrome extension records browser activity only during an explicitly-started work session; a server pipeline turns raw events into a deterministic timeline, then an AI reflection report (narrative, focus/distraction analysis, intent-vs-reality verdict, suggestions). Full product rationale, scope, and design decisions: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Build order and per-task acceptance criteria: [docs/ROADMAP.md](docs/ROADMAP.md) — **always check this before starting work; it's the authoritative "what's done / what's next."**

## Commands

```bash
pnpm install

pnpm dev                # all apps in dev mode (turbo)
pnpm build              # production builds, all workspaces
pnpm typecheck          # tsc across all workspaces
pnpm lint               # eslint .
pnpm format             # prettier --write .
pnpm format:check       # prettier --check .
pnpm test               # unit tests, all workspaces (no external services)

pnpm exec supabase start        # local Postgres/Auth via Docker — required before test:integration
pnpm exec supabase db reset     # (re)apply all migrations to the local DB
pnpm test:integration            # apps/web only: real /api/v1 route handlers against LOCAL Supabase
```

Per-workspace, from repo root:

```bash
pnpm --filter @watchme/web dev              # Next.js dashboard + API at localhost:3000
pnpm --filter @watchme/extension build      # writes apps/extension/dist, loadable via chrome://extensions → Load unpacked
pnpm --filter @watchme/shared test          # or: cd packages/shared && pnpm exec vitest run
```

**Single test file:** `cd <package> && pnpm exec vitest run path/to/file.test.ts` (or drop `run` for watch mode). Integration tests live only in `apps/web/tests/integration/` and use their own config: `cd apps/web && pnpm exec vitest run --config vitest.integration.config.mts tests/integration/sessions.test.ts`.

**Local dev environment override:** the extension's only configuration is its API base URL (defaults to production). To point a local build at `localhost:3000`, set `apps/extension/.env.local`:
```
VITE_WATCHME_API_URL=http://localhost:3000
```
then rebuild. Changing this (or any `host_permissions` in `manifest.config.ts`) requires **removing and re-loading** the unpacked extension in Chrome — a plain reload does not always re-grant new permissions.

Local magic-link emails are never sent to a real inbox — they land in the local Mailpit UI at `http://127.0.0.1:54324`.

## Architecture

**Monorepo, pnpm + Turborepo.** Three workspaces: `apps/web` (Next.js dashboard + `/api/v1/*`), `apps/extension` (Chrome MV3), `packages/shared` (Zod contracts). `packages/shared` exports raw TypeScript (`exports: "."` → `./src/index.ts`, no build step), consumed directly by both apps via `workspace:*` — this is why it needs no `tsup`/build config and why editing it doesn't require a rebuild step for the consuming app's dev server.

**The one rule that matters:** anything crossing the extension↔API↔database boundary is a Zod schema defined once in `packages/shared`, never duplicated. Shipped extensions can't be force-updated, so `/api/v1` is versioned and the event/session schemas are additive-only — do not change an existing field's shape; add a new optional field or a new API version instead.

**Auth model — two separate paths, never mixed:**
- Web dashboard: Supabase cookie session, refreshed by `apps/web/middleware.ts` → `lib/supabase/middleware.ts` on every request. `/api/` paths are explicitly skipped from that cookie logic (see the early-return in `updateSession`).
- Extension: **never talks to Supabase directly.** It exchanges a one-time code (generated by a logged-in user at `/connect-extension`, stored server-side only as a hash) for a token pair via `POST /api/v1/auth/extension`, then refreshes through `POST /api/v1/auth/refresh`. This means the extension's entire config surface is one base URL — swapping the auth backend later is a server-side change only. Client-side logic: `apps/extension/src/lib/auth.ts` (refreshes ~60s before expiry, retries once on a 401).

**Extension service worker (MV3) holds no state in module scope** — it is killed and restarted constantly by the browser. State lives in `chrome.storage.session` (current capture state, resets on browser restart — see `background/state.ts`), `chrome.storage.local` (auth tokens, survives restart), and IndexedDB (the event buffer, keyed by `clientEventId` so retries can never duplicate a row — see `background/buffer.ts`). `reconcile()` in `background/sessions.ts` runs on every service-worker wake and treats the server's `GET /sessions/active` as ground truth, adopting or clearing local state to match. Listeners (`background/capture.ts`) must be registered synchronously at the top level of `background/index.ts` — Chrome requires this to re-bind them after a restart.

**Privacy filter is a pure-function choke point**, not scattered checks: `background/filter.ts`'s `transition()` is the single place every focus change passes through, and it is what decides same-tab navigation vs. blur+focus, blocklist redaction (which structurally cannot carry a URL/title — `RedactedEventSchema` has no such fields), and incognito exclusion (yields a `null` context, zero events). Being pure functions of `{current, next, at, blocklist, cause}` is what makes the privacy rules unit-testable without a real Chrome environment (`background/filter.test.ts`).

**Idempotency is enforced at both ends of the event pipeline**, not just one: client-side, `enqueue()` keys IndexedDB rows by `clientEventId` so a re-enqueued retry overwrites instead of duplicating; server-side, the `events` table has `UNIQUE(session_id, client_event_id)` and the ingest route upserts with `ignoreDuplicates: true`. A batch can be replayed in full with zero side effects.

**Session lifecycle uses the database as the concurrency boundary**, not application logic: `sessions` has a **partial unique index** (`WHERE ended_at IS NULL`) enforcing "one active session per user" at the Postgres level. `POST /sessions` first checks for an active session, and if a race loses (Postgres error `23505`), falls back to fetching the winner rather than erroring — this is why "starting twice returns the same session" holds even under concurrent requests. Auto-ending idle sessions (`>60min` with no events) runs as a `pg_cron` job calling a `SECURITY DEFINER` Postgres function (`supabase/migrations/20260719150200_auto_end_idle_sessions.sql`), not an external scheduler or serverless cron — it needs nothing configured outside the migration itself.

**Supabase grants are always explicit.** This project's Supabase version does not auto-expose new tables to `anon`/`authenticated`/`service_role` — every migration that creates a table must include explicit `grant` statements matching its RLS policies, or every query against it fails with a permission error that looks unrelated to RLS. Check the existing migrations in `supabase/migrations/` for the pattern before adding a table.

**LLM provider abstraction rule (from ARCHITECTURE.md §8, applies once M3 lands):** all model calls will go through a single `lib/llm.ts` exposing `complete(task, messages, schema)`; no other file may import a provider SDK or name a specific model. Not yet built — noted here so M3 work doesn't scatter provider calls across files before the abstraction exists.

**Multi-agent pipeline (M3+, not yet built):** Session Compiler (deterministic, no LLM) → Activity Interpreter (cheap/fast model) → Reflection Analyst (best available model) → Memory Indexer (V2, embeddings). Each stage is a separate Inngest step for independent retry/resumability. The Compiler is explicitly the most important reliability decision in the system — the dashboard must render a useful timeline even if every LLM call fails.

## Local dev gotchas (learned the hard way this session — avoid re-discovering)

- This machine runs low on RAM with Docker Desktop's WSL VM up. If `pnpm lint`, `pnpm typecheck`, or `pnpm build` crash with an out-of-memory error, try `wsl --shutdown` first, and prefer `pnpm exec turbo run <task> --concurrency=1` over the parallel default when memory is tight.
- Keep the web app on **one host** (`localhost:3000`, not `127.0.0.1:3000`) throughout a manual test — the Supabase auth cookie does not carry across different hostnames/ports, and a stray orphaned dev server on port 3000 will silently push your server to 3001, breaking the magic-link redirect (which is hardcoded to port 3000 in `supabase/config.toml`).
- `noUncheckedIndexedAccess` is on in `tsconfig.base.json` — array index access (`arr[0]`) is `T | undefined`; use a non-null assertion only after asserting length, per the existing test files.
