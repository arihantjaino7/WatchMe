# WatchMe AI — Roadmap: Milestones → Epics → Tasks

This is the build order for WatchMe AI, derived from [ARCHITECTURE.md](ARCHITECTURE.md). It exists to answer one question at any point in the project: **"what do I build next, and how do I know it's done?"**

**Ordering principle:** contracts and data first, AI last. The event schema is the hardest thing to change post-launch — it's baked into shipped extensions and historical data. LLM prompts are the easiest thing to change. So: build the skeleton end-to-end with real data flowing through it, then make it smart.

**Format.** Each milestone maps to a GitHub Milestone. Each epic maps to a tracking Issue (labeled `epic`) with its tasks as a checklist or sub-issues. Each task is sized to be **one PR**: independently buildable, independently testable, and leaves `main` in a working state. Every task lists its **acceptance criteria** — the test for "done," not a description of the work.

Estimates assume ~10 focused hours/week (solo, part-time).

## M0 — Skeleton & contracts (Weeks 1–2, Low complexity)

**Goal:** a deployed, empty product with the data contract frozen. Nothing observes anything yet — but auth works in production and every later milestone builds on a schema that won't need to change.
**Dependencies:** none.
**Status:** repo scaffold (E1) is done as of this commit — Next.js/extension/shared skeletons, tooling, CI all in place.

- [ ] **M0-E3-T2** — API version constant + `/api/v1` convention documented in `packages/shared`. _AC: exported `API_VERSION` consumed by both extension and web without duplication._

**M0 exit criteria:** you can log into the deployed dashboard with a real account, and `packages/shared` has a tested, versioned contract that M1 and M2 build against without modification.

## M1 — Capture pipeline (Weeks 3–5, High complexity — MV3 lifecycle is the fiddliest part of this project)

**Goal:** real browser events, generated by real use, land durably in the production database.
**Dependencies:** M0 (contract + deployed auth).

### Epic M1-E1: Extension auth handoff

- [ ] **M1-E1-T1** — `POST /api/v1/auth/extension` — one-time-code exchange endpoint. _AC: integration test — valid unexpired code returns a refresh token once and is single-use (second exchange attempt fails)._
- [ ] **M1-E1-T2** — Web page `/connect-extension` generating the one-time code for a logged-in user. _AC: manual test — visiting the page while logged in shows a code/deep-link the extension can consume._
- [ ] **M1-E1-T3** — Extension: consume the code, store refresh token in `chrome.storage.local`, mint short-lived JWTs for API calls, auto-refresh on expiry. _AC: after connecting once, the extension can call an authenticated endpoint successfully after the JWT's TTL has passed (refresh happens transparently)._

### Epic M1-E2: Session lifecycle API

- [ ] **M1-E2-T1** — `POST /api/v1/sessions` (start, optional intent; returns existing active session instead of erroring if one exists). _AC: integration test — starting twice returns the same `sessionId`._
- [ ] **M1-E2-T2** — `POST /api/v1/sessions/:id/end`. _AC: ending sets `ended_at`, `end_reason='user'`; ending an already-ended session is a no-op, not an error._
- [ ] **M1-E2-T3** — `GET /api/v1/sessions/active` — recovery endpoint. _AC: returns `null` when none active; returns the session when one is._
- [ ] **M1-E2-T4** — Scheduled job: auto-end sessions idle >60min. _AC: a session with no events for 60+ minutes is auto-ended with `end_reason='auto'` on the next job run (test with a manually backdated `started_at`/last-event timestamp)._

### Epic M1-E3: Event capture & local privacy filter (service worker)

- [ ] **M1-E3-T1** — Tab/window/idle listeners emitting typed events per the shared schema. _AC: manual test — switching tabs, focusing/blurring the window, and going idle each produce the expected event shape in a debug log._
- [ ] **M1-E3-T2** — Local privacy filter: blocklist check, incognito exclusion, URL stripped to origin+path before it ever touches the buffer. _AC: unit test — a blocklisted domain never appears in the buffer with URL/title populated, only as `{type:'redacted', duration}`; incognito tab activity produces zero events._
- [ ] **M1-E3-T3** — IndexedDB event buffer with `clientEventId` generation. _AC: unit test — buffering the same logical event twice (simulated retry) still uploads with one stable `clientEventId`._
- [ ] **M1-E3-T4** — Batched idempotent upload (`POST /sessions/:id/events`) on a timer/count trigger, offline-safe (buffer grows, flushes on reconnect). _AC: manual test — disable network mid-session, generate events, re-enable network, confirm all buffered events arrive server-side exactly once (server enforces `UNIQUE(session_id, client_event_id)`)._
- [ ] **M1-E3-T5** — Service-worker restart recovery: reload state from `chrome.storage.session` + reconcile via `GET /sessions/active` on every wake. _AC: manual test — force-terminate the service worker mid-session (`chrome://serviceworker-internals`), confirm it recovers the active session on next wake without duplicating or losing events._

### Epic M1-E4: Popup UI

- [ ] **M1-E4-T1** — Popup: logged-out state → "Connect" (launches M1-E1 flow). _AC: manual test on a clean profile._
- [ ] **M1-E4-T2** — Popup: logged-in idle state → intent field + "Start session." _AC: starting creates a session server-side (verified via dashboard/DB) and popup transitions to active state._
- [ ] **M1-E4-T3** — Popup: active state → elapsed time, "End session," pause-capture toggle. _AC: ending a session flushes remaining buffered events and transitions the popup back to idle._

**M1 exit criteria:** run a real work session for an hour, close the laptop lid once, switch networks once — every real event still lands in Postgres exactly once, with no popup crash and no lost session.

## M2 — Deterministic timeline (Weeks 6–7, Medium complexity)

**Goal:** the product is already mildly useful with **zero AI**. This is also where dogfooding starts — and it starts here on purpose, per ARCHITECTURE.md §26 (validate before automating).
**Dependencies:** M1 (real events in the database).

### Epic M2-E1: Session Compiler (Agent 0)

- [ ] **M2-E1-T1** — Merge micro-switches (<5s) and compute per-domain durations from raw `events`. _AC: unit test against a fixture event stream with a known expected duration breakdown._
- [ ] **M2-E1-T2** — Focus-block detection (≥10min single context) + switch-count + idle-gap computation. _AC: unit test — a fixture with 3 distinct focus blocks and 2 idle gaps produces exactly that._
- [ ] **M2-E1-T3** — Apply the domain→category map from M0-E3-T3; persist `timeline_blocks` rows + denormalized `stats` JSON on `sessions`. _AC: integration test — running the compiler against a seeded session produces the expected row count and stats shape._
- [ ] **M2-E1-T4** — Wire compiler to run synchronously on `POST /sessions/:id/end` (no Inngest yet — that arrives with M3's AI stages). _AC: ending a session immediately makes its timeline queryable._
- [ ] **M2-E1-T5** — Golden-fixture test suite: 3–5 realistic session event logs with hand-verified expected output. _AC: suite runs in CI; becomes the regression net for every future compiler change._

### Epic M2-E2: Dashboard — sessions list & detail (timeline only)

- [ ] **M2-E2-T1** — `GET /sessions` (paginated, with stats) + sessions list page: date, intent, duration, focus %, top category. _AC: manual test — a logged-in user sees their real sessions from M1 testing._
- [ ] **M2-E2-T2** — `GET /sessions/:id` + session detail page rendering the colored timeline from `timeline_blocks`. _AC: manual test — timeline visually matches the known event log from a test session._
- [ ] **M2-E2-T3** — Empty state (no sessions yet) with install/connect instructions. _AC: manual test on a fresh account._

**M2 exit criteria:** run a real session on yourself, end it, and see an accurate deterministic timeline on the dashboard within seconds — no AI involved. **Start dogfooding daily from here on.**

## M3 — AI reflection (Weeks 8–10, Medium-High complexity — this is prompt/quality iteration, not plumbing)

**Goal:** ending a session produces a real reflection report. This is "MVP alive."
**Dependencies:** M2 (compiled timelines to feed the pipeline).

### Epic M3-E1: LLM provider abstraction & job orchestration

- [ ] **M3-E1-T1** — `lib/llm/index.ts` — `complete(task, messages, schema)` with per-task model routing (interpret→Gemini Flash w/ Groq fallback; reflect→best free-tier model), structured-output parsing against a Zod schema. _AC: unit test with a mocked provider — malformed model output is caught and retried/rejected, never silently passed through._ **Rule enforced here: no other file imports a provider SDK directly.**
- [ ] **M3-E1-T2** — Inngest project wired (dev + prod keys), `session/analyze` event triggered from `POST /sessions/:id/end`. _AC: ending a session enqueues a visible job in the Inngest dev dashboard._
- [ ] **M3-E1-T3** — Pipeline skeleton as Inngest steps: Compiler (move from M2's synchronous call) → Interpreter → Analyst, each a separate step with independent retry. _AC: killing the process mid-pipeline (simulated) resumes from the last completed step, not from scratch._
- [ ] **M3-E1-T4** — Failure UX: `analysis_status` states (`pending`/`running`/`complete`/`failed`) surfaced on the session detail page with a manual "retry" action if a stage fails permanently. _AC: manual test — force a provider error, confirm the timeline still renders and retry works._

### Epic M3-E2: Activity Interpreter (Agent 1)

- [ ] **M3-E2-T1** — Prompt + schema: group timeline blocks into labeled "work episodes," classify ambiguous activity using titles, flag distraction candidates. _AC: run against 3 dogfooded sessions from M2, manually verify episode grouping is sane._
- [ ] **M3-E2-T2** — Persist Agent 1 output as an intermediate artifact (for debugging and for Agent 2's input). _AC: inspectable in DB/logs independent of the final report._

### Epic M3-E3: Reflection Analyst (Agent 2)

- [ ] **M3-E3-T1** — Prompt + schema: narrative, focus assessment, distraction analysis, intent-vs-reality verdict, 1–3 evidence-grounded suggestions. _AC: report references specific timeline evidence (domains/times), not generic advice — checked against the prompt-eval fixtures below._
- [ ] **M3-E3-T2** — Persist to `reports` (versioned), include `model_info`/`tokens_used` for observability. _AC: two consecutive analyses of the same session produce two report versions, not an overwrite._
- [ ] **M3-E3-T3** — Prompt-eval harness: fixture sessions + assertion checks (e.g. "report must mention the declared intent," "must not exceed N generic-sounding phrases"). _AC: harness runs on demand (not necessarily CI-blocking, given LLM nondeterminism) and catches an intentionally-broken prompt in a manual trial._

### Epic M3-E4: Report UI

- [ ] **M3-E4-T1** — Session detail page renders the full report below the timeline: narrative → focus → distractions → intent-vs-reality → suggestions. _AC: manual test against a real dogfooded session._
- [ ] **M3-E4-T2** — Loading/pending/failed states matching `analysis_status`. _AC: manual test covering all four states without a page reload glitch._

**M3 exit criteria:** end a real session on yourself and get a report that tells you something true and non-obvious about how you worked. This is the moment to pause and validate with a handful of real users before M4 polish.

## M4 — Trust & polish (Weeks 11–12, Medium complexity)

**Goal:** shareable with 10 strangers without embarrassment or risk.
**Dependencies:** M3.

### Epic M4-E1: Privacy & settings

- [ ] **M4-E1-T1** — Settings page: blocklist editor (read/write `user_settings`), AI on/off toggle, extension connection status. _AC: adding a domain to the blocklist causes it to redact on the very next captured session (manual test)._
- [ ] **M4-E1-T2** — `GET /me/export` — full JSON export (sessions, events, timeline, reports). _AC: exported JSON round-trips through a schema validator; contains everything the account has._
- [ ] **M4-E1-T3** — `DELETE /me` — full account + cascade deletion (auth user, all rows). _AC: after deletion, no row referencing the old `user_id` remains in any table (verified by direct DB query in test)._

### Epic M4-E2: Reliability & abuse hardening

- [ ] **M4-E2-T1** — Rate limiting on ingest endpoints (per-user, via Upstash free tier or equivalent). _AC: load test exceeding the limit returns 429s instead of degrading the DB/LLM quota._
- [ ] **M4-E2-T2** — Recording indicator (extension icon badge while a session is active). _AC: manual test — badge visibly differs between idle and active states._
- [ ] **M4-E2-T3** — Plain-English privacy page, linked from the extension popup and dashboard footer. _AC: content review — accurately reflects M1's actual capture behavior, discloses free-tier LLM data handling._

### Epic M4-E3: Ship

- [ ] **M4-E3-T1** — Extension release pipeline: versioned build artifact via GitHub Action. _AC: a tagged commit produces a downloadable zip matching `manifest.json` version._
- [ ] **M4-E3-T2** — Chrome Web Store submission (submit early — review latency is measured in days). _AC: listing submitted with privacy justification for each requested permission._

**M4 exit criteria:** you'd feel comfortable handing this to a stranger and walking away.

## M5 — Beta loop (ongoing, complexity varies)

**Goal:** find out if the reflection is actually useful to someone other than you.
**Dependencies:** M4.

- [ ] **M5-T1** — Onboard ~10 real beta users; direct feedback channel (not a form — a conversation).
- [ ] **M5-T2** — Weekly digest email (V1.5's retention lever): summarizes the week's sessions, links back to the dashboard. _AC: a scheduled job sends one email per active user per week with correct data._
- [ ] **M5-T3** — Iterate report prompts against real (consented) user sessions, expanding the eval harness with each new failure mode found.

## M6 — Memory & Q&A (V2, Week 16+, High complexity)

**Goal:** sessions become a queryable memory. Only start this after M5 shows people actually return to read reports.
**Dependencies:** M5 signal that the base product retains users.

- [ ] **M6-T1** — Agent 3 (Memory Indexer): embed session summaries into the `memories` pgvector table (schema already exists from M0). Fire-and-forget after Agent 2.
- [ ] **M6-T2** — RAG retrieval over `memories` scoped to `user_id`.
- [ ] **M6-T3** — Chat UI on the dashboard for cross-session questions.
- [ ] **M6-T4** — Baseline calibration ("your typical Tuesday") once enough sessions exist per user.

## Cutting under time pressure

If a milestone is running long, per ARCHITECTURE.md §26: cut category-override UI (hardcode the map), Google OAuth (magic link only suffices), report versioning UI. **Never cut:** the local privacy filter, idempotent event ingestion, or the deterministic compiler — these are the trust and reliability foundation everything else sits on.
